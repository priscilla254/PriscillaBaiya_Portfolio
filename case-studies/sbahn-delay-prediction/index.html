Berlin S-Bahn Delay Prediction

This project uses synthetic data, not real S-Bahn Berlin or Deutsche Bahn operational data. The objective of this project was to determine if a trip can be called delayed before it departs, using only information that would already be known before departure.

The problem

A trip is delayed when delay_minutes is 6 or more. About 3% of trips meet that rule, so a model that always says "on time" is right 97% of the time and still misses every single delay. Accuracy would be misleading here, which is why the search objective and every reported number downstream is F1 on the delayed class. The objective of this project was to determine if a delay can be predicted from information that would already be known before departure.

What I built

An end-to-end pipeline: Pandera-validated ingestion of seven related tables into typed Parquet, a leakage-audited feature set, a LightGBM classifier tuned with Optuna under proper time-series cross-validation, a full evaluation layer (sliced error analysis, calibration, TreeSHAP), and the engineering scaffolding around it — 48 tests, GitHub Actions CI, a Dockerfile, a Makefile pipeline, and a batch scoring entry point that takes a new table in and returns predictions out.

Full implementation, tests, and reports are in the repo.

How it works

Every column was checked against one question: would this value already be known before departure? Two columns failed that test and were dropped — a per-line "delay propensity" score and a per-incident severity weight. Validation is a 5-fold TimeSeriesSplit that walks forward through January–October only. The operating threshold is chosen on those out-of-fold predictions, and November–December is touched exactly once, after every choice is already locked.

As the data was heavily imbalanced, I tried 2 approaches to improve the model's performance: class weighting and resampling. Both hurt holdout F1; it fell from 0.874 (no weighting) to 0.734.

Results

Treatment Development F1 Holdout F1
No weighting (shipped) 0.297 0.874
Class weights 0.379 0.818
Class weights, threshold sweep 0.634 0.818
Class weights plus resampling 0.435 0.734

The shipped model is the unweighted one. It is fit once on January–October and scored once on November–December, at a threshold of 0.30 chosen on the development window only: 793 caught delays, 91 missed, 162 false alarms, out of 21,426 holdout trips — F1 0.862.

That 0.862 is lifted by strike days. 93.6% of strike-day trips are delayed, and F1 there is 0.962. On ordinary days it is 0.717. The weaker slices — the ring lines S41/S42 and the commute peaks — are weaker because they carry more of that ordinary-delay case. TreeSHAP on the same holdout confirms that: a live strike is one feature worth about +5 log-odds on its own, while an ordinary delayed trip only reaches the cutoff by stacking smaller signals — recent per-line delay rate, weather, peak hour.

What I'd do next

  1. Replace the synthetic feed with real data, and rebuild the leakage audit against that schema from scratch.
  2. Keep the same evaluation discipline on real data — time split, threshold chosen on an earlier window, ordinary days reported separately from disruption days — since the gap between them is likely to reappear in a different shape.
  3. Re-fit entirely rather than reuse these hyperparameters or the 0.30 cutoff, which describe this synthetic file only, and recheck calibration, the ring lines, and the commute hours before anyone treats a call as operational.

Finding

Resampling and class weighting both looked like they should help an imbalanced target. Both hurt holdout F1. The first time-series fold trains before any strike has happened, then has to score one. Overweighting the delayed trips in that fold cannot teach a flag that it has never seen.
