Turning messy Excel benchmarks into a queryable pipeline

An ETL pipeline for construction cost benchmarking — Excel ingestion with validation, a SQL Server warehouse, embedded BI dashboards, and a Groq-powered assistant that answers cost questions in plain English instead of SQL.

Placement year · Proof of concept, built solo

9 endpoints FastAPI backend covering ingestion, validation, AI, and BI
2 Groq features read-only NL-to-SQL, and fact-grounded report drafting
Batch-tracked every upload validated, errored rows downloadable as CSV
Dockerized BI Superset dashboards embedded via guest token, not iframed blind

Construction cost benchmarking runs on spreadsheets — every project lands as its own Excel workbook, with its own quirks and its own errors. Comparing costs across projects meant someone manually reconciling that mess by hand. This project asked: what would it take to turn that into a proper pipeline — one where an upload gets validated automatically, lands in a real database, and can be queried by anyone on the team, not just whoever knows SQL?

The problem

Two separate audiences needed the same underlying data. Analysts wanted to slice cost data by project, sector, and cost element — the kind of thing a BI dashboard handles well. But non-technical stakeholders just wanted answers to direct questions — "what's the average cost per m² for this sector?" — without learning SQL or waiting on someone else to run a query. Building for only one of those audiences would have left the other exactly where they started.

Approach

The pipeline separates ingestion, storage, and consumption into distinct stages, so the AI layer and the BI layer both read from the same validated source of truth rather than from the raw spreadsheets directly.

Full backend, ingestion engine, and Superset config are in the repo.

Two AI features, two different guardrail problems

The natural-language query assistant takes a question like "Show top 10 Level2 elements by total cost", uses Groq to generate the corresponding SQL, and returns both the query and the result — so the answer is always auditable, not a black box. Because this sits in front of a real database, the endpoint enforces hard guardrails: single-statement queries only, must start with SELECT, and any mutating or DDL keyword (INSERT, UPDATE, DELETE, DROP) is blocked outright before execution.

The report-drafting service solves a different problem: generating client-facing tender report narrative — an executive summary, commercial analysis, and next steps — without letting the model invent figures. Every number in the output comes from a "deterministic facts" object built directly from the database (tender sums, adjustments, budget totals); Groq (llama-3.3-70b-versatile) only writes the surrounding prose, under an explicit instruction not to alter or invent any value, and not to reference the database, AI, or internal IDs in the client-facing text. If the Groq call fails for any reason, the service falls back to a deterministic templated paragraph built from the same facts — the report still generates, just without the polish.

Why Superset runs as a separate service

Rather than bolt BI logic into the FastAPI app, Superset runs as its own dockerized sidecar — avoiding dependency conflicts with the backend's own environment, and keeping BI runtime concerns (caching, worker processes, metadata storage) out of application code entirely. Dashboards are embedded into the React frontend via a guest-token endpoint rather than a raw iframe, and the SQL Server login backing them is scoped to read-only access.

What I'd do next

  1. Extend the ingestion engine beyond Excel — CSV and direct database imports, so the pipeline isn't tied to one file format.
  2. Add automated tests around the AI SQL guardrails specifically, since that's the highest-risk surface in the system.
  3. Move the AI report-draft endpoint from returning structured context to generating full narrative reports, closer to what a project manager would actually read.

Stack

FastAPI (Python) · React + TypeScript (Vite) · SQL Server · Groq API · Apache Superset · Docker

Backend surface

Upload & validate → batch summary, error counts, error detail, CSV export → AI query → AI report draft → Superset guest token. Nine endpoints, one consistent batch model running through all of them.

Guardrail · Query

The AI query endpoint rejects anything that isn't a single SELECT statement — INSERT, UPDATE, DELETE, and DROP are blocked before they ever reach the database.

Guardrail · Report drafting

Numbers come only from a facts object built from the database — the model is explicitly instructed never to invent or alter a figure, and falls back to a templated paragraph if the Groq call fails at all.

Why this matters

Same underlying pattern as the age-estimation work: take something that produces a plausible-looking answer, and make sure it can't quietly do damage — bias in a model, or an unchecked write in a database.
