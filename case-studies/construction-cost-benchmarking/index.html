Making the case for a centralised cost database

A self-authored proposal and proof of concept for a traditional construction consultancy still running cost benchmarking through spreadsheets — arguing for, then building, a centralised database, and testing whether a free BI tool could avoid an ongoing licensing cost.

Placement year, Costplan Services · Research proposal → proof of concept, built solo

$735.91/mo Power BI embed cost that sent us looking for an alternative
Superset: dropped free and self-hosted, but dashboard quality didn't hold up
Star schema 5 fact tables, 6 dimension tables, three levels of cost granularity
Signed off presented to all three directors; phase 2 (AI layer) now approved

Costplan is a quantity surveying consultancy — the kind of traditional, relationship-driven firm where decades of project cost data live in individual Excel workbooks, one per project, each with its own quirks. Comparing costs across projects meant someone manually reconciling that mess by hand. There was no formal database, no servers, and no existing appetite for one — which meant the real first task wasn't technical. It was making the case that centralising this data was worth doing at all.

Starting with a proposal, not a build

Rather than being handed a spec, I wrote a reverse brief — a self-authored proposal to the company's directors, structured the way a consultancy would present to a client: problem statement, objectives, scope, approach, deliverables. The first version proposed a master Excel template, a Python cleaning script, and Power BI dashboards on top, with a proper database scoped in as a longer-term deliverable.

The directors' feedback reshaped the whole direction. Power BI, they pointed out, only added real value for benchmarking — comparing costs across many past projects — not for day-to-day tender analysis, where QSs were already comfortable working in Excel and a dashboard added nothing they didn't already have. That pushback is what narrowed the scope correctly: the database wasn't there to replace how QSs already worked, it was there to make benchmarking possible at all, since without structured data that goal was going nowhere.

The data model

Construction cost data has real structure once you look past the spreadsheets: every cost belongs to a project, a specific cost stage (concept, tender, final account), and traces down through increasingly granular levels — from elemental totals ("the frame cost £800k") to standardised components ("which is broken into steel, concrete, decking..."). That structure became a star schema.

Full schema definitions and the ETL logic that populates them are in the repo.

The Power BI vs. Superset trade-off

Once the pipeline reached the point of embedding dashboards into a web app, Power BI's own embed pricing came out at roughly $735.91/month — too expensive to justify at this stage of the project for a company this size. That cost problem is what triggered a trial of Apache Superset, an open-source, self-hostable BI tool, as a free alternative.

I built it properly, not as a throwaway test: Superset ran as its own Dockerized sidecar service, with curated read-only BI views in SQL Server, and dashboards embedded into the React frontend via guest tokens rather than a raw iframe. It solved the cost problem outright.

It didn't solve the actual problem. Once embedded and running against real data, Superset's dashboard quality and visualisation capability simply didn't hold up against Power BI — the charts, interactivity, and polish were a clear step down. Verdict: abandoned. Power BI remained the preferred tool for the actual benchmarking output, cost included, and the Superset work was folded into the proposal as evidence the alternative had been properly tested rather than dismissed on assumption.

The AI layer, prototyped alongside

With the database and BI decision settled, the same PoC included two Groq-powered features, each with its own guardrail problem to solve. A natural-language query assistant lets a QS ask "Show top 10 Level2 elements by total cost" and get back generated SQL plus results — read-only, single-SELECT-only, with any mutating or DDL keyword blocked outright before execution.

A report-drafting service generates client-facing tender report narrative — executive summary, commercial analysis, next steps — while keeping every number locked to a "deterministic facts" object built directly from the database. Groq only writes the surrounding prose, explicitly instructed never to alter or invent a figure, with a templated fallback if the API call fails outright.

Where this landed

I presented the full proof of concept to all three company directors, split into two phases: Phase 1, the database and Power BI benchmarking dashboards; Phase 2, extending it with a natural-language layer on top of the data using Azure OpenAI. It was signed off, with a delivery timeline and a budget approved for the tooling to build it properly.

What I'd do next

  1. Build out the SSIS or Python-based automation for the ingestion pipeline, rather than the current manual-trigger PoC.
  2. Add automated tests around the AI SQL guardrails specifically, since that's the highest-risk surface in the system.
  3. Extend the elemental breakdown to Level 3 (assembly/product) once enough projects are in the system to make that granularity useful rather than sparse.

Why this matters

Same underlying instinct as the age-estimation work: test the plausible-sounding alternative properly before trusting it, and make sure nothing downstream can quietly do damage.
