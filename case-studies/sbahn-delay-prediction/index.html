Berlin S-Bahn Delay Prediction

The data is synthetic — not real S-Bahn Berlin or Deutsche Bahn operational data, disclosed up front in the repo. The point of this project isn't the specific numbers; it's the discipline: can a trip be called delayed, before it departs, using only information that would already be known on the platform — without a single column that secretly encodes the answer?

The problem

A trip is delayed when delay_minutes is 6 or more. About 3% of trips meet that rule, so a model that always says "on time" is right 97% of the time and still misses every single delay — accuracy is actively misleading here, which is why the search objective and every reported number downstream is F1 on the delayed class, not accuracy. The useful question underneath that is narrower: can delay be called from information that would already be sitting on the departure board, before the trip happens?

What I built

An end-to-end pipeline, not a notebook: Pandera-validated ingestion of seven related tables into typed Parquet, a leakage-audited feature set, a LightGBM classifier tuned with Optuna under proper time-series cross-validation, a full evaluation layer (sliced error analysis, calibration, TreeSHAP), and the engineering scaffolding around it — 48 tests, GitHub Actions CI, a Dockerfile, a Makefile pipeline, and a batch scoring entry point that takes a new table in and returns predictions out.

Full implementation, tests, and reports are in the repo.

How it works

Every column was checked against one question, written down in the feature dictionary rather than applied ad hoc: standing on the platform before departure, would this value already be known? Two columns look like excellent features and aren't — a per-line "delay propensity" score and a per-incident severity weight — both built from the outcome they'd be predicting, so both are excluded, with a test in CI that fails if either ever reaches the model's input set. Validation follows the same discipline: a 5-fold TimeSeriesSplit walks forward through January–October only, the operating threshold is chosen entirely on those out-of-fold predictions, and November–December is touched exactly once, after every choice is already locked.

The most interesting result came from a fix that made things worse. Delay is heavily imbalanced (about 32 on-time trips per delayed one), so the obvious move is class weighting, and the obvious next move after that is resampling on top of it. Resampling made the holdout score worse, not better — F1 fell from 0.874 (no weighting) to 0.734. The cause turned out to be a cold-start specific to this data: the two in-sample strikes land inside particular cross-validation folds, so some folds train with zero exposure to the strike flag ever being true. Oversampling delayed rows in a fold that has never seen a strike just copies rows the model has no feature to explain them with — it can't learn "strikes mean delay" from a flag that's always 0. Once both strikes are inside the final training set, the unweighted model doesn't need the help at all.

Results

Four imbalance treatments, same search, same holdout. The treatment that scored worst during tuning won on the holdout that actually matters — the opposite of what tuning alone would suggest.

Treatment Development F1 Holdout F1
No weighting (shipped) 0.297 0.874
Class weights 0.379 0.818
Class weights, threshold sweep 0.634 0.818
Class weights plus resampling 0.435 0.734

The shipped, unweighted model is fit once and scored once at an operating threshold of 0.30 (chosen on January–October only): 793 caught delays, 91 missed, 162 false alarms out of 21,426 holdout trips — F1 0.862. That number is propped up by strike days: 93.6% of strike-day trips are delayed and the model scores F1 0.962 there, against F1 0.717 on ordinary days. Slicing by line, hour, and weather all reduce to the same distinction — the ring lines (S41/S42) and the commute peaks are weaker because they carry more of the gradual, ordinary-delay kind the model finds genuinely harder, not because of uneven disruption exposure (I checked — line sample sizes are balanced and strikes hit the whole network, not specific lines). TreeSHAP on the same holdout confirms the mechanism directly: a live strike is a single feature worth roughly +5 log-odds almost by itself, while an ordinary delayed trip only gets close to the cutoff by stacking several moderate signals — recent per-line delay rate, weather condition, peak hour — which is a genuinely closer call.

What I'd do next

  1. Replace the synthetic feed with an official data agreement, and rebuild the leakage audit against that schema from scratch.
  2. Keep the same evaluation discipline on real data — time split, threshold chosen on an earlier window, ordinary days reported separately from disruption days — since the gap between them is likely to reappear in a different shape.
  3. Re-fit entirely rather than reuse these hyperparameters or the 0.30 cutoff, which describe this synthetic file only, and recheck calibration, the ring lines, and the commute hours before anyone treats a call as operational.
